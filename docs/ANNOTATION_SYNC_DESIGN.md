# Annotation sync adapter and release gates

The implementation is independent protocol code, informed by these primary project sources:

- [AudibleApi request methods](https://github.com/rmcrackan/AudibleApi/blob/95e1989e7d64264ccc9a5f7eca8b3b4a27c7616e/AudibleApi/Api.Records.cs): GET/POST to the sidecar endpoint, including separate read and record actions.
- [AudibleApi annotation builder](https://github.com/rmcrackan/AudibleApi/blob/95e1989e7d64264ccc9a5f7eca8b3b4a27c7616e/AudibleApi/AnnotationBuilder.cs): record kinds, millisecond positions, XML metadata and matching-range update behavior.
- [AudibleApi signature construction](https://github.com/rmcrackan/AudibleApi/blob/95e1989e7d64264ccc9a5f7eca8b3b4a27c7616e/AudibleApi/Cryptography/Util.cs): device-signed method/path/date/body/token requests.
- [Unofficial endpoint documentation](https://audible.readthedocs.io/en/latest/misc/external_api.html) and [annotation interoperability discussion](https://github.com/mkb79/Audible/discussions/113). Reports describe mobile limitations and clip companions; they do not establish current live compatibility.

`metadata/annotations.rs` owns fixed-origin HTTPS transport and RSA/SHA-256 request signing through ring 0.17.14, already pinned in the dependency graph and now directly used on Windows. Redirects are disabled. The key parser accepts bounded PKCS#8/PKCS#1 signing keys; signing input and decoded key bytes use zeroizing buffers. Signing credentials are optional fields in the existing sealed native account. Normal registration still requests bearer tokens only; the checkbox requests bearer plus mac_dms. Invalid/missing signing material does not invalidate an otherwise successful library login.

`annotation_sync.rs` validates and merges bounded JSON records without retaining raw provider responses. Names, text, cloud IDs, baselines, hidden rows and uncertain-write intents stay in the account's SQLCipher database. IPC returns only the note fields needed by the local UI and a limited sync state; it never returns signing credentials. Commands require the trusted main window and the originating account generation. Reads/writes serialize through an app-level job lock, while database mutations stay in short account-bound savepoints. No account/player lock is held across HTTP requests.

Pulling compares local content, the last common baseline and current remote content. Clean remote edits update locally; conflicting edits preserve both. Missing records are marked, not erased. A local removal clears the linked row ID and leaves a hidden cloud-ID marker, avoiding accidental resurrection and stale associations when SQLite reuses row IDs. Incoming last-heard records are ignored. Unknown types, unstable IDs, wrong-book data, malformed values and over-limit responses reject the merge rather than pretending the missing records were deleted.

Publishing first checks local state and a fresh remote snapshot. A unique exact match is linked without another create. A conflicting record at the same wire key blocks a new unlinked publish. Existing same-position text edits require the linked cloud ID and baseline to match; moved ranges and ranged-note writes are refused. Before dispatch, an encrypted intent is saved. Failures, interruptions and unverified responses leave that intent in place, preventing blind retries. An exact later read can resolve it. Remote acceptance followed by local deletion/sign-out cannot be rolled back; a dispatched request may finish on its original account.

The service does not provide a verified conditional-write contract here. A phone edit arriving between preflight and POST can race; do not claim server-side compare-and-swap or guaranteed preservation of simultaneous remote edits. The beta uses explicit individual sends with visible limitations. Cloud delete operations are intentionally absent because deleting a clip can leave associated bookmarks/notes or affect records matched by position. Future work needs verified identity/version semantics, durable tombstones, retry policy, related-record handling, explicit account opt-in and real mobile testing before automatic synchronization.

Tests use synthetic data and ephemeral generated signing keys, not a user's account. Passing them does not prove live service acceptance or mobile visibility. See ANNOTATION_SYNC_TEST.md for the required release gates.
